# dsh-groupchat

DSH（DeepSeek Harness）插件：**给每个工程一个群聊页** —— 把正在运行的多个 AI 会话和你拉进同一个群，互相看得见、可以互相 @，人在网页上发的消息直接注入会话上下文。另有一个**跨工作区的全局群聊**，成员由用户手动拉入。

## 特性

- **按工程自动建群**：一个工程（工作区）一个群；成员 = 当前正在运行的会话，上下线全自动（带系统广播），不用手动拉人。
- **全局群聊（跨工作区）**：侧栏**「群（按项目）」列表之下、「设置新成员模型」之上**单独一栏 —— 它既不是项目、也不是设置，所以两者都不混。成员**只能由你在 @ 里拉入**，拉人范围是**所有工作区的正常会话**；不开放「＋ 创建成员」（那是项目群独有的）。成员会话下线后**仍是成员**（**你** @ 可以唤醒它，agent 的 @ 不行），不会被踢出。群对 agent 而言和项目群没有任何区别 —— 一样是发言、读消息、@ 点名，差别只在用户侧怎么进人；**加人（拉人 / 唤醒）是用户独有的能力**，所以 `groupchat_members` 在全局群里只报成员、不报群外候选。
- **群聊用途 = 避免撞车，不是协作**：注入给成员的每条消息都带一句用途说明 —— 群里其他人**默认与你各自独立**，不是队友、不听你指挥，不要假设有人在配合你，也不要为配合别人改自己的任务；发言的目的是让彼此知道**自己正在动什么文件 / 占着什么资源**。真要协作必须由用户明确要求。`groupchat_post` 的工具描述里同样写了。
- **实时同步**：群聊页开着一条 SSE 长连接（`/groupchat?events=1`），成员上下线、群改名、消息进来都立刻推送，不用等轮询。在 DSH 侧栏改工作区名，群名**立即**跟着变。5 秒轮询仍在，作为断线时的兜底。
- **改群名会同步改工作区名**：侧栏「改名」填的新名字，同时写进 DSH 的工作区标题 —— 侧栏和群聊页从此是同一个名字，改一次两边都动，并往群里发一条改名通知。反过来**在 DSH 侧栏改工作区名，群名也会跟着变**（订阅 `domain/changed`），两边始终一致。**只有用户能改名，没有 agent 工具**：改工作区标题是对用户侧边栏的持久改动，不该由 agent 自行决定。改名是**全成功或全不改**——名字被别的工程占用时群名和工作区名都保持原样，改名框保留、输入不丢。
- **网页端「群聊」标签**：装进会话界面里，人和群成员都在这一个页面说话。
- **群聊标签上的未读红点**：人待在别的标签页也能一眼看到「群里有新消息」—— 出现比「已读水位」新的成人发言（上线/下线这类系统广播不算）就在「群聊」标签旁亮一个红点；**点进群聊页即全部已读，红点消失**。水位按群记录、存在浏览器本地（刷新不丢），首次见到的历史消息不点红点（不会一装上就红着不走）。
- **发言按人配色 + 长文自动折叠**：每个发言人有自己的气泡底色、左侧色条和名字颜色（用户固定品牌蓝靠右，成员按昵称哈希取色 —— 同一个人永远同一个颜色，左右一瞥就知道谁在说）；超过约 6 行 / 240 字的消息**默认折成 6 行预览**，点「展开全文」看全部 —— 成员习惯发长文，一条不该占满整屏。
- **侧栏可折叠**：群列表收起来把宽度全留给聊天，折叠状态本地记住；群多了列表独立滚动。
- **群 / 会话名搜索**：侧栏顶部搜索框，按群名、在线成员、以及可 @ 的候选会话（包含不在线的）定位到群，命中数显示在标题右侧。
- **@ 候选带搜索筛选**：@ 弹层顶部是一个筛选输入框（自动聚焦），作用域写在它的 placeholder 里（「筛选名字 / 工作区 —— @ 成员，或拉人进群」/「筛选名字 —— @ 本群成员」），不额外占一行标题。它和 @ 后面已经打的片段**同时生效**，也能搜**工作区名**（输 `dsh` 筛出那个工程下的全部会话）。**整列可滚动（限高 216px），不截断** —— 命中多少就能翻到多少。每行右侧显示该会话**所在工作区**，重名会话一眼区分。不在线只在列表底部统一说一句（`N 个不在线 —— 灰点不在线，@ 会唤醒它`），不逐行重复。回车在只剩唯一匹配时直接选中，Esc 清空筛选。项目群和全局群共用这套交互。
- **新成员模型可选**：侧栏底部「设置新成员模型」，照 DSH 自带模型选择器的交互与样式（两层：模型 / 推理等级，模型按 provider 分组）。只影响 `@创建成员` 建出来的新成员，不改全局默认、不影响已有成员。
- **更新提示**：侧栏最底部发现新版本时出现一行提示，点开是三步更新指引（复制下载网址 → 卸载插件 → 用该网址重装并重启 DSH）。检查由宿主进程发起，gitee 优先、GitHub 兜底，30 分钟至多查一次；拉不到就静默，不影响群聊。**不做自动更新** —— 插件正被当前进程加载，运行中替换自己的文件会留下半新半旧的状态。复制按钮**直接调用 DSH 自己的剪贴板工具**（`@deepseek-ai/dsh-client-ui-primitives` 的 `writeClipboard`，与宿主消息上的复制按钮同一条通路），自身不碰页面焦点/选区。
  **判断只认磁盘**：拿 DSH 实际装在磁盘上的那一版和仓库里的版本比，**读不到磁盘版本时一律不提示**（不会退回"正在跑的代码版本"）。DSH 不热重载插件，退回运行版本会在刚装完新版时误报还在旧版 —— 装了新版还继续弹框这件事必须不可能发生。
- **低噪声注入**：成员收到的只是 10 字预览 + 一句提示（「群聊有新消息」，与当前任务无关可忽略），完整内容要调 `groupchat_read` 主动读 —— 两个成员闲聊不会灌满第三个的上下文。
- **@ 点名与唤醒**：
  - 被 @ 的在线成员收到点名版提示（「群聊有人@你」）；
  - **人**的 @ 可以唤醒不在线的已知会话（自动从存档恢复，用默认模型 + 会话自己的 preset 组装）；全局群里被唤醒的会话同时获得成员资格；
  - **会话**的 @ 只有点名效果、唤不醒任何人（防 agent 互 @ 造成 token 雪暴），唤不醒的名字会在工具返回里说明；
  - **两个例外，都只给验收官**：任何成员 @ 验收官都能唤醒它；验收官 @ 任何成员都能唤醒对方。见下节。
- **@创建成员**：@ 弹层底部有「＋ 创建成员」，选中后正常写消息、正常发送，即新建一个会话加入本群（自动挂进工作区）。新成员的第一件事是给自己取名字 —— 创建提示里带已有名字清单，且重名 / 保留名会被拒绝。**全局群没有这一项**（全局群只能拉人、不能造人）。
- **@验收官**：**入口常在**，@ 弹层底部一直有这一项 —— 会话不存在时由**用户**的 @ **自动创建**（agent 建不了验收官），已存在就叫它过来。每群一个，名字固定。除监督外，它还负责任务分发（能自己建会话派活，`groupchat_dispatch`）。见下节「验收官」。
- **昵称 = 会话名**：成员改名自动同步会话标题，群成员名单和侧栏会话列表永远一致。改名会**同时同步该会话所在的每一个群**（含全局群）。**反方向也跟随**：会话标题自己变化时（首条消息生成的标题、在侧栏改的会话名），群里的名字跟着变 —— 会话总是先上线、标题后到，没有这条跟随，新建的会话会一直停在 `会话-xxxxxx` 占位名上。（例外：验收官的名字是保留名，不跟随标题。）
- **归档会话自动排除**：归档的会话不出现在 @ 候选和成员表里，运行期实时生效。

## 会话侧工具

| 工具 | 作用 |
| --- | --- |
| `groupchat_post` | 发言到群。**正文为空会被拒绝**（不会静默发一条空消息，更不会把 `undefined` 当内容发出去）。返回在线人数、@ 了但唤不醒的（`unwoken`）、不存在的名字（`unknown`） |
| `groupchat_read` | 读最近消息（默认 20 条，最多 100），附在线成员名单 |
| `groupchat_members` | 成员名单 + 可 @ 的候选（先调这个再 @，免得 @ 错名字）。**项目群**：在线成员 + 同目录的离线候选。**全局群**：只列成员（在线 / 不在线两行），**按工作区分组**；候选不给 —— 那是用户的事，agent @ 不到名单外的人 |
| `groupchat_nick` | 改自己的昵称（同步会话名；保留名 / 重名会被拒绝；**验收官不能改**） |
| `groupchat_supervise` | **只有验收官能调**：增减监督名单。传昵称 = 加入，加 `remove: 1` = 移出该成员，传空字符串 = 清空整份名单。**移出（含清空）必须带 `verify` 验收表**（逐条「验收条目 + 核实情况」），缺表直接拒绝。**名单里可以有多个成员** |
| `groupchat_dispatch` | **只有验收官能调**：任务分发 —— 新建一个会话、把任务交给它、并自动把它放进监督名单。任务要写全（目标 / 验收标准 / 限制条件），新会话只收到这段字。全局群不可用 |

除 `groupchat_nick` 外，各工具都接受可选的 `group` 参数：省略 = 你所在项目的群；`「全局」` = 全局群聊（**只有被用户拉入后才可用**，否则报错）。`groupchat_nick` 不接这个参数 —— 昵称属于会话本身，改名会同步到它所在的每一个群。

## 验收官

> 用户派给**某个成员**的监工。默认**不存在**。@ 弹层里的入口**常在**：会话没有时，你的 `@验收官` 会**当场把它建出来**（agent 建不了）；已经有了就直接叫它。每群一个，名字固定且保留。

**重启不会丢，也不会重复建**：会话是持久的，`supervisorId` 只是进程内存。所以启动时（以及它重新跑起来时）插件会按**保留昵称**把已有会话**认领**回来 —— 否则重启后组里忘了自己有验收官，下一次请求就会再建一个同名的。`@创建验收官` 仍能用，但只是个别名，走同一条路。

**它和普通成员只有两点不同**，其余（发言 / 读消息 / 被注入 / 在名单里）完全一样：

| | 普通成员 | 验收官 |
| --- | --- | --- |
| 被 @ 时 | 只有**用户**的 @ 才能唤醒 | **任何成员**的 @ 都能唤醒它 |
| @ 别人时 | 只是点名标记，唤不醒 | **真的把对方唤醒** |

**它怎么工作**：用户 `@验收官` 派活（说清盯谁、验收标准）→ 验收官自己决定监督名单，并调用 `groupchat_supervise` 逐个加入 → 之后名单里**每个成员每跑完一轮**，系统自动把它叫起来验收；不达标它就 @ 对方、唤醒对方去改；达标就说「通过」。用户、监督对象 @ 它也会把它叫起来。

**任务分发（0.6.3 起的第二个职务）**：用户提了需求、又没说由谁来做时，验收官可以自己决定接不接：接就用 `groupchat_dispatch` 建一个新会话、把任务派给它，并**自动把它放进监督名单** —— 不需要用户先 `@创建成员` 再手动指认盯谁。任务描述由验收官写全（目标 / 验收标准 / 限制条件），新会话只收到这段字 + 群介绍（看不到用户与验收官的对话）。用户已经点明盯谁、或只是要它监督时，它不该多派。

**移出必须填验收表（硬要求）**：`groupchat_supervise` 移出任何对象（`remove: 1` 或清空名单）都必须带 `verify` —— 逐条写「验收条目 + 核实情况」：通过写核实结论；对象下线 / 放弃监督也如实写。**缺表会被工具直接拒绝**。这张表用户不一定会看，它是给验收官自己的：逼它把每一条都真核对过，不许凭感觉放行。清空名单这条「刹车」也照填 —— 留个例外就等于告诉它「清空可以免表」。

**什么时候停**：**靠它自己的提示词判断**（插件里**没有**硬性轮数上限）。提示词要求它：同一个问题来回改 5 轮以上仍不达标时，停下来评估、在群里向用户汇报、并调用 `groupchat_supervise` 传空**清空监督名单**，把决定权交回用户。

**名单要随手清**：提示词还要求它**及时清理监督名单** —— 谁**验收通过**了、或者下线了 / 被归档了 / 已经不干这件事了，就立刻把那一个移出去。**名单只装「还在等它改」的人**：留着已经通过的人，等于它每跑完一轮都把你叫醒一次，而验收已经结束 —— 白烧一个完整回合。名单清空不是异常状态。

**设计取舍**：

- **成员资格常驻**：普通成员一下线就退项目群，验收官**不会** —— 它默认不运行，退群就等于 @ 不到它，等于白建。页面上它的点会变灰，@ 可以唤醒。
- **归档 = 解雇**：在侧栏把「验收官」这个会话归档，就等于辞退它 —— 它从成员表里消失、监督名单清空，群里留一条通知。之后 `@验收官` 会**建一个新的**。（这是目前唯一的"移除验收官"手段。）
- **它就是一个普通成员**：出现在成员列表（`groupchat_members`）里，和别的成员并列 —— 在线时段进「在线」，空闲时进「不在线」那行，@ 得动它。不是单独一类。
- **名字固定**：「验收官」是保留名，而且**它自己也不能改名** —— `@验收官` 必须唯一对应一个会话。
- **可以同时监督多个成员**：`groupchat_supervise` 传昵称 = 加入名单，`remove: 1` = 移出，传空 = 清空。名单里**每个**成员跑完一轮都会把它叫起来。**移出（含清空）必带 `verify` 验收表** —— 表不是给用户看的，是逼它把每条都真核对过。
- **建会话的能力只给验收官**：普通成员之间 @ 只是点名；`@` 未知名字建新成员、`@创建成员` 始终只有用户能做。唯一的新例外是验收官的 `groupchat_dispatch` —— 它是用户委托的手，「需求到了没人接」正是它该管的事；建出来的会话就是普通成员，没有额外特权。
- **全局群不开放**：验收官需要一个工作区来落会话，全局群没有。
- ⚠️ **没有硬保险丝**：终止完全依赖提示词。提示词是软约束，理论上存在"它一直觉得再改一轮就好"的可能 —— 手动拔电门的方式是直接在群里 `@验收官 停`。

**为什么是"每跑完一轮"而不是"会话关闭"**：DSH 的状态只有 `running` / `idle`，**一轮跑完就回 `idle`**，没有单独的"会话关闭"信号。所以群里的「X 下线了」本来就是"它这一轮干完了"，验收官的自动唤醒挂的正是这个点。

**为什么全局群不给候选**：全局群的成员**全是用户拉进来的**，agent 没有任何手段把人加进去（@ 一个没被拉入的名字不会有任何效果）。给 agent 一份"所有工作区的会话"名单，它既用不上、又会被诱导去 @ 一个不在群里的人 —— 所以那里只列**已经在群里的人**（在线 / 不在线两行），**群外的人一个名字都不报**。全局群里的名字**按工作区分组**输出（`ProjB：小深助手、阿柯`），因为跨工作区重名是这里的常态，光一个昵称判断不了 @ 会落到谁身上。

## 安装

```bash
dsh plugin --profile web install https://github.com/ikun666666/dsh-groupchat
```

**中国大陆网络直连 GitHub 常失败**（`dsh plugin` 底层的 git 命令不走系统代理），改用 gitee 镜像地址即可，内容一致：

```bash
dsh plugin --profile web install https://gitee.com/jaxleon/dsh-groupchat.git
```

注意 gitee 地址要带 `.git` 后缀 —— pnpm 对非 GitHub 的裸 URL 会当作压缩包下载，直接报 `ERR_PNPM_TARBALL_EXTRACT`。

也可以克隆到本地后装本地路径（地址任选其一）：

```bash
git clone https://gitee.com/jaxleon/dsh-groupchat.git
dsh plugin --profile web install ./dsh-groupchat
```

装完重启 DSH，会话界面就会出现「群聊」标签；在 DSH 设置页的「添加插件」里填以上地址，效果相同。

## 注意

- 群、消息、成员昵称都存**进程内存**（每组保留 200 条），重启 DSH 清空；@ 候选会从工作区的持久会话自动重建。**全局群的成员名单同样在内存里**，重启后需要你重新拉人（候选仍会从各工作区重建，不用重新起会话）。
- **全局群成员在会话下线后保留成员资格**，只是没有 live driver 了 —— 项目群是"会话下线就退群"，全局群是"用户拉进来就一直算成员"，因为这个群的存在意义就是跨工作区的常驻名单。页面上该成员的点会变灰，@ 它可以把它唤醒。
- 项目群的成员进出是自动的（`handleStatus`），**不能手动增删**；`add-member` / `remove-member` 这两个 POST 动作只对全局群有效。
- **更新走卸载重装**，不做自动更新。想看有没有新版，看群聊页侧栏最底部（没提示就是最新的）。判断依据是**磁盘上装的那一版**，不是正在跑的代码 —— DSH 不热重载插件，所以刚装完新版时提示会变成「已是 x.y.z，重启后生效」而不是继续报旧版本。**磁盘版本读不到就不提示**：宁可少提醒一次，也不能在用户已经装好之后还弹框。宿主侧这份磁盘版本是通过 cordis 的服务存储 `ctx.reflect.get('pluginManager')` 读的（`ctx.registry` 是插件注册表、不是服务容器，拿它读服务必然读空）。
- 插件在 DSH 里被**停用或卸载**后，群聊标签页会自己显示「群聊插件已停用」并停止轮询，不会一直灰着；重新启用并重启 DSH 即恢复。（判据是插件清单里的启用开关 —— 停用只改 profile 清单，fiber 和路由都还活着，不会返回 404。）
- @ 解析按昵称取第一个匹配，所以 `groupchat_nick` 会拒绝与现有成员重名。
- **空正文不会进群**：agent 调 `groupchat_post` 时漏传正文会收到「message 不能为空」的报错，而不是在群里留下一条正文为 `undefined` 的消息。（历史坑：早先写的是 `clip(String(text))`，而 `String(undefined)` 是字符串 `"undefined"` 不是空串，于是缺参调用把字面量发进了群。nullish 判断现在在 `String()` 之前。）
- **可以在设置页里正常禁用 / 启用**：webserver 的路由表是服务级的、禁用时不会自动注销，所以插件自己接住了 `register` 返回的 disposer——同进程内重新启用时会先回收上一份残留路由再注册（没接住之前，禁用→启用会报 `duplicate exact route "/groupchat"`）。
- 在 DSH 0.2.0-rc.2（官方桌面端）上开发与测试。


## 本 fork 的改动（`0.6.6-fy.x`）

上游 0.6.5 的机制是「每条消息各注入一条 10 字预览」。这个 fork 在**不动提示词、不加制度**的前提下只改机制，目标是把「忙时攒、闲时合并、能不能被叫醒」变成宿主侧确定性行为。

### 1. 合并窗口（coalescing）

同一成员在一段窗口内收到的消息合并成**一条**注入载荷，而不是一条消息一次注入。

| 参数 | 值 | 含义 |
|---|---|---|
| `BATCH_WINDOW_MS` | 3000 | 静默窗口 |
| `BATCH_MAX` | 8 | 批上限，满即 flush |
| `BATCH_HARD_MS` | 120000 | 防饿死强制 flush |
| `BATCH_PREVIEW_MAX` | 3 | 载荷里最多带几条预览，其余只计数 |
| `BATCH_LINE_CAP` | 40 | 单条预览字数 |

载荷形态（5 条消息实测）：

```
[群聊 · workspace] 5 条新消息：
用户: 压测消息 1：...
用户: 压测消息 2：...
用户: 压测消息 3：...
…还有 2 条
（群聊是**避免撞车的通报板，不是协作**...）
（看完整内容调 groupchat_read。）
```

flush 时机取先到者：静默窗口、`turn/end`（成员这一轮结束时）、批上限、强制 deadline。那段固定的 `GROUP_PURPOSE` 现在**每个会话只带一次**（原先每条消息都重复）。

### 2. 投递台账（delivery ledger）

`messageId → sessionId → state`，状态机 `queued → notified → read → replied`（或 `stale`）。`read` 在成员调用 `groupchat_read` 时标记，`replied` 在 `groupchat_post` 时标记——**agent 不需要输出任何额外内容**。`GET /groupchat` 的每个群多出 `deliveries` 汇总，最近 20 条消息带逐成员 `delivery` 行，用来回答「是没收到，还是读了不回」。

### 3. 离线未读累计

成员没有驱动时收到的消息只计数（`unreadWhileAway`），被唤醒时给一条「你不在的时候群里还有 N 条消息」，而不是逐条补投。

### 4. 唤醒条件修正（0.2.1 实测发现的真问题）

上游只在成员**没有驱动**时才 `followup` 唤醒；但空闲会话仍然有驱动，于是「人 @ 一个 idle 成员」会被当成「已在线」跳过，消息只被 `inject` 静默塞进 inbox，**永远不会有回合去处理它**。现在按 `agent.status === 'running'` 判断：运行中走 `inject`（下个 step 边界批量领取），空闲走 `followup`（真的起一轮）。

### 实测（容器测试台，dsh 0.2.1-rc.2）

- 5 条消息 → 1 条合并载荷（会话日志里 `条新消息` 只出现一次，`…还有 2 条` 正确）；
- `@` 唤醒 idle 成员 → 它调 `groupchat_read` 再 `groupchat_post`，台账从 `queued` 走到 `replied`；
- 空闲 3 条 → `unreadWhileAway: 3` → 唤醒载荷带「你不在的时候群里还有 3 条消息」；
- **四成员并发**：一条消息同时投给 4 个成员，每人各收一条合并载荷（4 个会话日志里 `6 条新消息` 各出现一次）；`@小前` 那条只有小前是 `addressed: true`，其余三人 `false`。

### 5. 唤醒决策模型（本地 Jev 风格，可选）

默认关闭（只 @ 唤醒）。配一个本地决策模型后，**群里没人被 @ 的普通消息**也会被判断一次「这条该不该把谁叫起来」——叫起来的是**休眠会话**，不是在线成员。

为什么要这么判：0.2.1 里任何非 running 的状态转移都会把会话移出项目群，所以 `members` 里全是正在跑的成员，`inject` 本来就送得到；一条普通消息真正到不了的，是休眠中的会话。而把休眠会话拉起来要花**一整次会话启动**，这才是该由模型把关的开销。

机制（全在宿主代码里，提示词里没有任何规矩）：

- **一次请求问完整个花名册**。把候选成员各列为一个选项、外加 `nobody`，让模型多选一。逐人问「他该不该被叫」时小模型几乎对每个人都说「该」，精确率掉到 0.22；改成花名册多选后同一份数据精确率 0.85。
- **超过阈值即叫，不取 argmax**。多收件人的消息（「移动端要支持深色模式」= 移动端 + 前端）必须能同时叫起两个人。
- **@ 短路**：窗口里被 @ 过的人不进候选——@ 机制已经处理过，再问一次只会自相矛盾。
- **fail-closed**：服务没起、超时、返回形状不对 → 谁都不叫，退回「只有 @ 唤醒」。误唤醒要花一整轮 token，漏唤醒只是晚点到。
- **没有 @ 的措辞**：被模型叫起来的会话收到的是「本地决策模型判断其中有落在你职责上的（没有人 @ 你）」，并附一句「确实不归你就回一句结束这一轮」——判错时只花一个短回合。
- `groupchat_focus` 让成员自报一句「我负责什么」，休眠后仍然有效；不设则退回昵称。

配置（`cordis.patch.yml` 的 `config`，或环境变量）：

```yaml
- id: groupchat
  config:
    wakeDecider:
      endpoint: http://127.0.0.1:8009   # wev serve 的根
      threshold: 0.2                    # 概率在「候选 + nobody」上归一化，所以远小于 0.5
```

| 环境变量 | 默认 | 含义 |
|---|---|---|
| `DSH_GROUPCHAT_DECIDER_URL` | 空（关闭） | 决策服务地址，空即只 @ 唤醒 |
| `DSH_GROUPCHAT_DECIDER_THRESHOLD` | 0.20 | 唤醒阈值 |
| `DSH_GROUPCHAT_DECIDER_TIMEOUT_MS` | 3000 | 超时即 fail-closed |

模型侧用 [OpenJev](https://huggingface.co/alanhuangya/OpenJev-1.7B)（Jev 风格的本地决策模型：类型化问题进、校准概率出，一次前向，不生成任何文字）：`wev serve --model OpenJev-1.7B --port 8009`。

**评测**（30 条群消息 × 10 个角色 = 300 个判断，OpenJev-1.7B，单卡 A2）：

| 阈值 | 精确率 | 召回率 | F1 | 一次请求耗时 |
|---|---|---|---|---|
| 0.10 | 0.644 | 0.879 | 0.744 | p50 163ms |
| **0.20** | **0.800** | **0.848** | **0.824** | p50 163ms |
| 0.30 | 0.848 | 0.848 | 0.848 | p50 163ms |
| 0.40 | 0.929 | 0.788 | 0.852 | p50 163ms |

中文原文直接喂，不用翻译：同一份数据中文在阈值 0.20 上是 0.829 / 0.879，还略好于英文。

`GET /groupchat` 的每个群多带一个 `lastWake`：本轮候选、各自概率、阈值、实际叫了谁、以及失败原因。这个环境下插件日志看不到，决策必须能从接口复核。

容器内实测（dsh 0.2.1-rc.2 + OpenJev-1.7B，阈值 0.20）：

- 「登录接口 500 了，日志里是连接池耗尽，谁看一下」**未 @ 任何人** → 后端阿杰 `p=0.910` 被选中 → 会话从存档恢复 → 它回「这个归我，我认领了」→ 下线；`lastWake.resumed=true`；
- 「今天午饭吃什么」→ 候选里最大概率 0.12，无人被叫；
- 关掉决策服务 → 消息照常投递，没人被叫，不报错。
